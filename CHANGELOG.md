- **Fix: duplicate Discord notifications, and Web Push silently failing 100% of the time** — reported live: users got the GvG "Day 3" daily-task notification 6 times in a row. Root cause: `event-reminders`' per-guild "lock" (meant to guarantee a reminder is only sent once) used `.upsert()` against `guild_config`, which never errors on a primary-key conflict — it just silently overwrites. Under load, a slow invocation can outlast its own 1-minute cron tick and overlap with the next one; each overlapping invocation reads a stale "not yet locked" snapshot and both send. Confirmed directly against production: the 6 duplicate messages lined up exactly with 6 consecutive cron ticks (00:01-00:06 UTC) that all timed out waiting on that same slow invocation. Fixed by switching all 5 lock-acquisition sites (standard events, GvG daily tasks, GvG Saturday, SvS, Calamity) from `.upsert()` to a real `.insert()`, which correctly raises a conflict error against `guild_config`'s actual `(guild, key)` primary key — the existing "already locked, skip" handling then works as originally intended, regardless of how much invocations overlap. Separately found while investigating: Web Push (browser) notifications have been failing for **every single subscription, 100% of the time** — `sendNotification` (the `web-push-neo` library) takes 3 positional arguments, but the code called it with one wrapped object, so the library validated the wrapper instead of the real subscription and rejected every single one with "You must pass in a subscription with at least an endpoint," even though all 10 stored subscriptions were perfectly valid. Fixed to call it with the correct 3-argument signature. **648/648 Vitest unit tests green** (+4 new regression tests locking in both fixes). Deployed via the Supabase CLI; confirmed live post-deploy (clean, non-timing-out cron ticks).
