# discord-verification-worker

Always-on Discord Gateway listener for the player-verification feature (screenshot -> role + nickname + roster). This is the only piece of the feature that can't run on Supabase Edge Functions, because reacting to a message posted in a channel requires a persistent Gateway (WebSocket) connection, which a stateless, invoked-per-request Edge Function cannot hold open.

This worker holds no verification business logic. It detects an image posted in a configured verification channel and gives the player immediate feedback as **reactions only** (⏳ while the screenshot is processed, then ✅/❌) -- the `discord-profile-verification` Supabase Edge Function owns every actual decision (OCR, validation, database writes, role resolution, nickname change) and posts the detailed confirmation/error message itself, so the worker never adds a duplicate text reply. On a verification that the roster confirmed (`role: "guild_member"`) it assigns the configured verified-member role (see below); it deliberately does **not** on the visitor or pending outcomes -- see ADR-020. It also registers and serves two slash commands at startup (`/profile`, `/absent`), forwarding reads/writes through the same service-role database paths the web app uses. It runs a trivial HTTP listener (`GET /` -> 200 once Discord is connected, 503 before) -- that exists **only** because Render's simplified web-service tooling has no "background worker" type and a Web Service expects a bound port for health checks; nothing is meant to actually call it.

Requires Node.js >= 22 (the `ws` package is pinned as the Realtime transport for `@supabase/supabase-js`, which avoids the WebSocket resolution crash some runtimes hit at startup).

## Deploying on Render

1. **New Web Service** pointing at this GitHub repo (this is a monorepo -- the worker lives in this `discord-verification-worker/` subfolder alongside the main app).
2. **Root Directory**: set this to `discord-verification-worker` if your Render flow exposes that field. If provisioning through a tool/API that doesn't expose a root-directory field (as happened here), the equivalent is folding the `cd` into the commands instead:
   - **Build Command**: `cd discord-verification-worker && npm install`
   - **Start Command**: `cd discord-verification-worker && npm start`
3. **Instance type**: any paid, always-on tier -- **not the free tier**, which spins down on inactivity and would drop the Gateway connection (and miss verification messages) until the next request wakes it back up.
4. **Environment variables** (Render dashboard -> Environment) -- `SUPABASE_URL`, `VERIFICATION_FUNCTION_URL`, and `DISCORD_WORKER_SECRET` were set when the service was provisioned; `DISCORD_BOT_TOKEN` and `SUPABASE_SERVICE_ROLE_KEY` were deliberately left out (highly sensitive, added by the account owner directly in the dashboard, never passed through an assistant tool call):
   - `DISCORD_BOT_TOKEN` -- same bot token already used for slash commands (Developer Portal -> Bot). Needs `Manage Roles` + `Manage Nicknames` permissions granted when the bot was invited (re-invite required if it was added with `permissions=0`).
   - `SUPABASE_SERVICE_ROLE_KEY`
   - `SUPABASE_URL`
   - `VERIFICATION_FUNCTION_URL` -- the deployed `discord-profile-verification` function URL, e.g. `https://<project-ref>.supabase.co/functions/v1/discord-profile-verification`
   - `DISCORD_WORKER_SECRET` -- a randomly generated secret shared with the Edge Function (also set as a Supabase Edge Function secret under the same name). Authenticates worker -> Edge Function calls; not related to `DISCORD_PUBLIC_KEY` (which authenticates Discord -> `discord-bot-interactions` instead). Must be the exact same value in both places.
   - `DISCORD_MEMBER_ROLE_ID` *(optional)* -- Discord role ID granted automatically after a verification the roster confirmed (e.g. a `Verified` role). **Only** on the `guild_member` outcome: `server-provisioner.js` auto-wires the per-guild fallback to a tag-bearing `[TAG] Member` role, so granting it to a visitor or a pending recruit would hand out exactly what the roster gate withholds (ADR-020). Falls back to the per-guild `guild_config` key `discord_member_role_id` when unset; if neither is configured the feature is silently disabled. Requires the bot to have `manage roles` and its own role positioned **above** the target role.

Without `DISCORD_BOT_TOKEN` and `SUPABASE_SERVICE_ROLE_KEY` set, the process exits immediately at startup with a clear "Missing required environment variable" log line -- that's expected until both are added.

## Per-guild setup (admin side, no code)

In the app: **Admin -> Discord Notifications -> Player Verification (Screenshot OCR)**:
- **Verification Channel ID**: the Discord channel (e.g. `🔐・verification`) to watch. Empty = disabled for that guild.
- **Only grant the guild role to players already on the roster**: the ADR-020 gate, stored as `guild_config` key `discord_verification_require_roster`. Off by default (a guild with no value keeps the old behaviour, where a screenshot could create the roster entry it was checked against). On, the member list is the authority: the guild role goes only to a player already in it, matched on their in-game UID -- or on their pseudo when that roster row still holds no real UID, in which case the UID read off the screenshot is written to it. Anyone else gets `[PENDING]`, nothing is written to the roster, and the audit/officer channel gets a durable message naming them.
- **Verified Member Role ID** (per-guild fallback for `DISCORD_MEMBER_ROLE_ID`): add a `discord_member_role_id` row in `guild_config` with the Discord role ID as its value.

There's no "role ID" to configure -- roles are resolved dynamically by name. On that Discord server, create a role named exactly after the guild's bracketed tag (e.g. `[PR1M]`), one named `[VISITOR]`, and one named `[PENDING]`, all positioned **below** the bot's own role (Server Settings -> Roles -> drag the bot's role above them) -- a Discord-level constraint, not something any code here can work around. Without a `[PENDING]` role a held verification falls back to `[VISITOR]`, and without either it only gets a nickname; it never gets the guild role.

**A tag is only ever matched within one game server.** The candidate guilds are those sharing the channel guild's own `guilds.server_number`, so a guild on another game server carrying the same tag resolves to nothing and its members get `[VISITOR]` here -- and cannot be blocked from their own server either. A channel guild with **no** server number can resolve no tag at all: set it in the app (Settings -> Guild), or every screenshot there becomes a visitor. Two guilds sharing a tag on one server is reported to the officer channel and never guessed.

## Slash commands

Registered globally on startup (merged into any existing global commands, so other commands are never wiped):

- `/profile [user] [ingame_name]` -- shows a member's FGF roster stats (role, Overall Power, Fleet, Tech, Flagship, Champs, Crew, timezone) as an embed; resolved via the target's linked account (`discord_account_links` -> `accounts`) or an in-game pseudo search in `guild_members`. Public on success, ephemeral when nothing is found.
- `/absent <start_date> <end_date> [reason]` -- declares a full absence for the caller's linked guild. Dates are validated (`YYYY-MM-DD`, end >= start) and the write goes through the same `gm_upsert_player_absence` service-role RPC the web + Edge Function paths use. Always replies ephemeral.
- `/update-stats [power] [glory]` -- updates the caller's Overall Power and/or Glory in the roster. Power goes through `gm_upsert_player_metrics`, Glory through `gm_upsert_player_glory` under the ISO Monday of the current week (`week.js`, the same rule as the app's `getWeekStartIso`). Both RPCs answer with an `ok` flag rather than raising, so both are checked: **a refused write fails the reply**. It used to call `gm_submit_event_score`, which exists in no database, and report success anyway.
- `/setup-server <guild> [server_number] [clean_mode]` -- Administrator only. Refuses a guild that is not registered in the tool, and refuses to invent a game-server number: that number scopes guild-tag resolution (ADR-020) and the `server_admin` role. Creates `[VISITOR]`, `[PENDING]`, the `[TAG]` member role and the R4/R5 roles, the categories and channels, and wires the verification and audit channels into `guild_config`. It no longer wires `discord_member_role_id`.
- `/mystats [weeks]` -- the caller's attendance per event type (SvS, GvG, Shadowfront, DTR, Arms Race) against their guild's pooled rate, from `gm_player_stats`. Ephemeral. It reports counts and computes **no** weighted score: the weighting lives in `src/core/scoring/reliability.ts`, shared by the admin page and the Portal, and a third copy here is how those two came to disagree once already.
- `/verifications [days]` -- officers (`ManageMessages`): players whose verification was held back by the ADR-020 roster gate, read from the `discord_verification_refused` audit rows. The guild comes from the verification-channel map or the caller's linked account, **never** from an option. Ephemeral, 20 rows, pings nobody.
- `/reconcile-roles` -- officers (`ManageRoles`): who holds the guild tag role without a roster row. Report first; removal only behind a confirmation button that only the officer who ran it can press, and only ever the tag role. **Needs Discord's privileged Server Members Intent**: enable "Server Members Intent" in the Developer Portal, then set `DISCORD_GUILD_MEMBERS_INTENT=true` on Render. The intent is opt-in because declaring it while the toggle is off makes the bot fail to log in entirely.
- `/power`, `/glory`, `/timezone`, `/challenges`, `/absence set|list|cancel` -- **forwarded** to the `discord-bot-interactions` Edge Function with the shared worker secret, and its reply relayed. Those five run the same validated `_shared/player-actions.ts` code the Player Portal uses; reimplementing them here would be a second copy that drifts. `/power` and `/glory` overlap with `/update-stats`, and `/absence set|list` with `/absent` and `/absences` -- kept because they exist on Discord and players may already use them.
- Also registered: `/link`, `/myinfo`, `/top`, `/absences`, `/call-to-arms`.

**One transport.** Discord delivers interactions over an Interactions Endpoint URL **or** the Gateway, never both. Measured 2026-09-28: `discord-bot-interactions` was invoked 0 times in 24 hours while `discord-profile-verification` was invoked 15, so the Gateway -- this worker -- is the live one. The worker owns every command definition and registers them on boot, globally and per guild; `scripts/register-discord-commands.mjs` was deleted for being a third registry that nothing kept in step.

**One Discord identity may hold several player accounts** since migration `20260927120000` (an administrator who is also a player). Every command that acts *as* the player resolves the link, keeps only the active accounts, and asks which one to use when there is more than one -- it never picks silently, because silently picking is how an admin's command lands on their player account. `/profile @someone` cannot ask them, so it says to search by in-game name instead.
