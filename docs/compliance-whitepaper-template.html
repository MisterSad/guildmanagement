1. Executive Summary & Scope

1.1 Mission & Nature of the Platform

The FGF Guild Management Platform is an out-of-game, web-based software-as-a-service (SaaS) companion dashboard designed solely to assist guild officers and players in organizing internal rosters, scheduling guild battle events, tracking aggregate statistical participation, and dispatching announcements via Discord webhooks.

The platform operates 100% externally and asynchronously from the video game client and its operational servers. It acts in the exact same legal and technical capacity as a collaborative spreadsheet (e.g. Google Sheets or Microsoft Excel) or an out-of-game Discord bot, providing community organization tools.

1.2 Fundamental Compliance Invariants

🛡️ Game Integrity & Non-Interference

  • Zero Client Hooks: No injection into game memory or executable space.
  • Zero Network Tampering: No packet interception or sniffing.
  • Zero Automation: No automated botting, macros, or gameplay actions.
  • Zero Private APIs: No unauthorized reverse-engineering of game endpoints.

🔒 Data Privacy & IP Safeguards

  • Zero PII Collected: No real names, emails, phones, or GPS coordinates.
  • Zero Game Assets: No copyrighted textures, sprites, or 3D models.
  • Ephemeral In-Memory OCR: Roster screenshots destroyed immediately after parse.
  • PostgreSQL 17 RLS: Kernel-level cryptographic tenant isolation.

2. Zero-PII & Privacy-by-Design Governance (GDPR & CCPA)

The platform was architected under strict Privacy by Design (PbD) and Data Minimization principles in full alignment with the European General Data Protection Regulation (GDPR - Regulation EU 2016/679), the California Consumer Privacy Act (CCPA), and child safety standards (COPPA).

2.1 Strict Absence of Personally Identifiable Information (PII)

The database contains zero real-world personal data. Below is an exhaustive audit of all data fields handled by the system:

Data Category Stored? Technical Implementation & Privacy Safeguard
Real Names / Surnames NO (0%) Only public in-game nicknames chosen by players are stored (e.g. "StarLord99"). No legal names are ever requested or accepted.
Personal Email Addresses NO (0%) Application database tables store zero real emails. Player accounts use internal synthetic tokens or pseudonymized login handles. Supabase Auth identity is strictly isolated.
Physical Address / GPS NO (0%) Zero geographical tracking or GPS coordinates exist. No device geolocation APIs are invoked.
Phone / SMS Numbers NO (0%) No telephony or SMS integrations exist.
Financial / Card Details NO (0%) SaaS subscriptions are handled 100% off-site by Stripe Hosted Checkout (PCI-DSS Level 1). Zero credit card numbers or billing addresses touch our database.
In-Game Passwords / Auth NO (0%) The platform never prompts for, accepts, or stores video game passwords, Google Play credentials, Apple IDs, or game session tokens.
IP Address Persisted NO (0%) IP addresses are never persisted in database tables. Cloud infrastructure logs undergo automated short-term rotation.
Timezone Offset Offset Only Only a non-identifying integer offset (e.g. +2 or -5) is stored to calculate guild battle countdowns relative to UTC.

🗑️ Data Minimization & Cascade Deletion

All member records maintain strict foreign key cascades (ON DELETE CASCADE). When an officer or member removes their profile, all related event participations, squad assignments, and score logs are instantaneously and permanently deleted from the database.

🚫 Zero Ad Trackers & Behavioral Telemetry

The client contains zero marketing SDKs, zero advertising cookies, and zero behavioral telemetry tools (no Facebook Pixel, no Google Ads, no data brokering). Data is exclusively used for guild roster display.

3.3 Ephemeral In-Memory OCR Processing (Zero Screenshot Storage)

To assist guild officers with roster management without manual typing, an Optical Character Recognition (OCR) pipeline is provided. The architecture guarantees that no user screenshots are permanently saved or stored:

  1. In-Memory Transit: The guild officer uploads a leaderboard screenshot over an encrypted TLS 1.3 channel to the ocr-guild-members Edge Function.
  2. AI Vision Extraction: Google Gemini Vision API parses the image in volatile RAM to extract numeric values (power, scores) and public pseudonyms.
  3. Immediate Bitmap Destruction: The screenshot bitmap is immediately destroyed from RAM upon parse completion. The platform maintains zero disk storage, zero S3/bucket image retention, and zero image archiving.
  4. Defensive Sanitization: Extracted values are strictly sanitized into plain integers before insertion into database tables.

5. Zero-Trust Security Model & Defensive Protections

The platform enforces a strict Zero-Trust Security Model: all requests require explicit cryptographic verification regardless of origin.

5.1 The Four-Role Access Control Model (RBAC)

Role Database & API Scope Security Isolation Boundary
super_admin Platform owner. Reads & writes all guild tenants for maintenance and global diagnostic logs. Single master account (HawkEye). Enforced via JWT verification + database role checks.
server_admin Reads & writes only guild tenants sharing their assigned game server_number. PostgreSQL RLS queries cross-checking guilds.server_number. Cross-server writes are blocked.
guild_admin Reads & writes strictly their single assigned guild tenant (e.g. ALPHA). PostgreSQL RLS engine isolation. Attempting to access another guild returns empty sets or 403.
member ZERO direct database access. Cannot read or write any database tables directly. Restricted to Player Portal. Communicates solely via the member-portal Edge Function.

5.2 PostgreSQL 17 Kernel Row-Level Security (RLS)

Tenant isolation is enforced directly within the PostgreSQL kernel via SECURITY DEFINER access functions with explicit SET search_path TO '' to prevent search path hijacking: 

-- Centralized Tenant Read Qualifier Function
CREATE OR REPLACE FUNCTION public.gm_can_read_guild_data(p_guild text)
RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER SET search_path TO ''
AS $$
  SELECT EXISTS (
    SELECT 1 FROM public.accounts a
    LEFT JOIN public.guilds g ON g.id = p_guild
    WHERE a.auth_user_id = (SELECT auth.uid())
      AND a.status = 'active'
      AND (
        a.role = 'super_admin'
        OR (a.role = 'server_admin' AND a.server_number IS NOT NULL AND a.server_number = g.server_number)
        OR (a.role IN ('guild_admin', 'R5', 'R4', 'admin') AND a.guild = p_guild)
      )
  );
$$;

5.3 Defensive Edge Function Hardening

🛡️ SSRF Webhook Whitelisting

The discord-webhook-proxy enforces strict hostname whitelisting (discord.com/api/webhooks/). Arbitrary destination URLs, loopback interfaces (127.0.0.1), and internal RFC 1918 private subnets are categorically blocked.

🔢 Defensive Score Bounding

All numerical submissions pass through parseSafeScore, bounding non-negative integer values to 500,000,000. This prevents integer overflow attacks, NaN corruption, and database schema errors.
