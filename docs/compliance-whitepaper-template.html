1. Executive Summary & Scope

1.1 Purpose of the Platform

The FGF Guild Management Platform is an out-of-game web application that helps guild leaders, officers and players of Foundation Galactic Frontier organise rosters, schedule guild events, track attendance and scores, and post announcements to their own Discord servers. It is free for every guild, with no paid tier.

The platform runs entirely outside the game client and the game servers. It works in the same capacity as a shared spreadsheet or a community Discord bot.

1.2 Foundational Principles

Game Integrity & Non-Interference

  • No client hooks: no injection into game memory or processes.
  • No network tampering: no packet interception.
  • No automation: no bots, macros or gameplay actions.
  • No private APIs: inputs are what users type or upload.

Data & IP Safeguards

  • Data minimisation: pseudonyms, player IDs, Discord IDs if linked, 24-hour sign-in IPs.
  • No game assets: open-source fonts and icons, self-hosted.
  • OCR: screenshots not stored; recordings staged privately, then deleted.
  • PostgreSQL 17 RLS: database-enforced tenant isolation.

2. Personal Data & Privacy by Design (GDPR)

The operator is established in France, so the GDPR applies whether or not the service is paid. The full notice is the Privacy Policy (privacy.html), whose inventory is exhaustive.

Retention

Enforced by scheduled database jobs, mainly gm_apply_data_retention() daily at 04:30 UTC: sign-in IPs 24 hours; codes, tickets and cached OCR text until expiry; call-to-arms answers 7 days; unactioned guild requests 14 days, their Discord handle erased 90 days after closure; audit log and pseudonym history 12 months; rosters and statistics while the guild uses the service.

Erasure

On request, through gm_erase_player and gm_erase_account. A player is anonymised: the pseudonym is replaced by a token from a salt that is never stored, UID and timezone cleared, absences and history deleted; the roster row survives unattributable so guild totals stay valid. Ban records are kept in full, as disclosed (Art. 17(3)).

No Tracking

No cookies, analytics, advertising SDKs or pixels. Browser storage holds only session and display state, strictly necessary, so no consent banner is required. The CSP connect-src limits the browser to the Supabase project and Sentry ingest.

Processors

Supabase (database, auth, storage, functions; EU database), Vercel (hosting), Google Gemini (OCR, wiki summaries), Discord (sign-in, notifications), Sentry (EU, diagnostics), Render (verification worker). Transfers outside the EU under standard contractual clauses or the EU–US Data Privacy Framework.

3.3 OCR Processing

  1. Screenshots travel in the request body over TLS to the ocr-guild-members Edge Function, are read by Google Gemini for the duration of the request, and are not stored. The transcribed text and a SHA-256 fingerprint of the image are cached in public.ocr_cache until expiry.
  2. Screen recordings (MP4, MOV or WebM; at most 64 MiB and 300 s) are uploaded by the browser to the private Storage bucket ocr-videos, where RLS lets only that guild's administrators upload, read or delete. The function reads the video with the caller's own token, sends it to the Gemini File API, then deletes the Gemini file and the stored object whatever the outcome; recordings left over from an interrupted scan are removed at the guild's next scan after one hour. Google deletes the file after processing or within 48 hours.
  3. Review before write: the officer sees a diff against the roster and confirms; a roster import is all-or-nothing.
Non-Affiliation

  • Structured logs: EdgeLogger emits JSON with correlation IDs and redacts credentials and tokens; browser errors go through a rate-limited RPC and Sentry with PII scrubbing.
  • Audit trail: administrative actions write to public.system_audit_logs, whose insert is reserved to the service role.

5. Security Model

5.1 Four Roles

Roles are stored in public.accounts.role, limited by a CHECK constraint to four values, and resolved from auth.uid() on every request — never from client-supplied data.

RoleScopeEnforcement
super_adminAll guilds; account provisioning, audit log, ticket console.accounts row resolved from the JWT.
server_adminGuilds on their own game server.RLS helpers compare guilds.server_number.
guild_adminTheir own guild only.gm_can_read_guild_data, check_user_guild_write_access.
memberNo direct table access; the Player Portal only.Every RLS read helper returns false; requests go through the member-portal Edge Function.

5.2 Row-Level Security

Every public table has RLS and FORCE RLS. Policies call SECURITY DEFINER helpers with SET search_path = '', which also refuse a session whose epoch was revoked (password reset, role change, suspension). Tables holding credential material are granted per column.

Not a control: is_subscription_active()

public.is_subscription_active(p_guild) still appears in 45 write policies, but it is an inert stub (a literal SELECT true, verified on production on 2026-10-04). It gates nothing; the app is free.

5.3 Player Portal Isolation

A player signs in with Discord and joins a guild with a join code and their UID, approved by an officer. Direct table queries from a member return nothing. The portal calls member-portal, which requires a platform-verified JWT, resolves the account from it (active status and current session epoch required) and derives the player's UID server-side; client-supplied identities are ignored.

5.4 Edge Function Protections

  • Authentication: verify_jwt is set per function in supabase/config.toml. Seven functions take no Supabase JWT because no session exists yet or the caller is not a user (sign-in, registration, guild requests, the cron-triggered reminder dispatcher, the Discord interactions endpoint verified by Ed25519 signature, the verification worker authenticated by a shared secret); the other seven require one.
  • Input validation: Zod schemas; scores bounded to 0–9,999,999,999.
  • Rate limits fail closed (sign-in, portal, OCR video budget).
  • Webhooks: Discord webhook URLs are stored server-side in guild_config, never supplied by the client at send time; only Discord hosts over HTTPS are accepted.
  • Secrets live in Supabase Vault or function environment variables, never in the repository.

6. Quality Assurance

Every push runs the CI pipeline; deployment jobs run only after all checks pass.

1. npm run type-check      zero TypeScript errors
2. npm test                Vitest suite, with a coverage floor
3. npm run build           production bundle, with an entry-size budget
4. npx playwright test     end-to-end tests against the built bundle in dist/,
                           incl. axe-core accessibility checks, CSP and asset errors
5. deno check / deno test  Edge Functions against an in-memory Supabase
6. migration replay        PostgreSQL 17 from scratch, schema fingerprint vs production,
                           SQL tests of RLS, grants and RPCs as each role

On 2026-10-04 the suite stood at 2,508 Vitest tests and 61 Playwright tests (CHANGELOG, phase M5). The number grows with every change: read the CI run rather than this line.
