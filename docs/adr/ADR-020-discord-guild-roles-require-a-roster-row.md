# ADR-020 — A Discord Guild Role Requires a Roster Row, on the Channel's Own Game Server

**Status**: Accepted
**Date**: 2026-09-28
**Supersedes**: nothing. Narrows the role-assignment rule recorded in `discord-verification-worker/README.md`.

## Context

The screenshot → role flow granted a guild's Discord role on the strength of a
guild tag read off an image by OCR, and **created the roster row itself** when it
did not find one. Two consequences, both verified against production on
2026-09-27:

1. **Anyone could join a roster with a picture.** A screenshot showing `[PR1M]`
   got the `[PR1M]` Discord role *and* an `INSERT` into ALPHA's
   `guild_members`. The check and the thing being checked were the same write.
2. **The tag resolved across game servers.** `resolveTagToGuild` scanned every
   tenant's `guild_config` rows globally and took whichever row iterated first on
   a collision. Nothing in the resolver knew that ALPHA, OMEGA and IMK are the
   three guilds of game server `#1058`; a same-tag guild on another server was
   indistinguishable from a sibling.

Two further defects widened the same hole:

- `discord-verification-worker/index.js` granted the extra
  `discord_member_role_id` role on **any** successful outcome, including the
  Visitor path — and `server-provisioner.js` auto-wires that key to a role it
  names `[TAG] Member`. No `discord_member_role_id` row existed in production
  yet, so the leak was armed and had not fired.
- `gm_find_player_by_uid`, used to veto a UID "registered elsewhere", is
  guild-blind: `WHERE uid = TRIM(p_uid) ORDER BY created_at DESC LIMIT 1`. Four
  UIDs exist in two guilds at once (ALPHA+PAIN, ALPHA+YARR, ALPHA+BABE), so the
  legitimate member of whichever guild was older was refused.

The owner's requirement is the inverse of the old behaviour: **the member list
in the Guild Management tool is the authority, and the Discord role follows it,
never creates it.**

## Decision

**1. A tag resolves only within one game server.**
`resolveTagToGuildOnServer(admin, tag, homeServerNumber, homeGuild)` replaces the
global scan. The candidates are exactly the guilds sharing the verification
channel's own `guilds.server_number`. A collision inside one server returns
`ambiguous` and is never guessed. A channel guild with no `server_number`
returns `home_server_unknown` and never widens back to a global scan. A server
number read off the screenshot that disagrees with the channel's own forces the
Visitor path even when the tag matched — strict when present, ignored when the
OCR could not read it, because that line sits at the bottom of the screen and is
often cropped.

**2. The roster decides, when the guild asks it to.**
`guild_config` key `discord_verification_require_roster`. Opt-in per guild: absent
means the historical behaviour, and only the exact string `'true'` enables the
gate. When it is on, a player who is not in that guild's `guild_members` is
refused with `not_on_roster`; nothing is inserted, ever.

Matching, in order, against one bounded read of the target guild's roster:

| On file | Outcome |
|---|---|
| the same in-game UID | accepted; stats updated, identity untouched |
| the same pseudo (NFKC, case-insensitive) and a **missing or placeholder** UID | accepted; the real UID is written onto that row |
| the same pseudo and a **different real** UID | refused (`pseudo_conflict`) — a rename or an impostor is an officer's call |
| two rows with the same lowercased pseudo | refused (`ambiguous_pseudo`) — `UNIQUE (guild, pseudo)` is case-sensitive, so it does not guarantee one row |
| nothing | refused (`absent`) with the gate on; inserted with it off |
| a read that came back at the cap or errored | refused (`scan_truncated`) — never reported as absent |

A placeholder UID is what `getUidStatus` in `src/modules/ocr/ocr.service.ts`
already calls invalid: missing, `TEMP-`/`TMP-`, non-numeric, or outside 6–10
digits. 11 OMEGA and 55 PSA rows carry one, generated by the roster OCR when the
member-list screen shows no UID; a UID-only gate would refuse those real members
forever, so the pseudo path exists to *claim* an unclaimed row and clean the data
on the way through. The last three rows above are refused **whether or not the
gate is on**: with it off, an `INSERT` would either collide with
`UNIQUE (guild, pseudo)` and surface as a meaningless `db_error`, or enrol
someone already present on a truncated read.

**3. `pending` is a first-class outcome, not a visitor.**
A refused recruit gets a role named `PENDING` when the server has one, else
Visitor, else a nickname-only patch — never the guild role, and never a nickname
carrying the tag being refused. The player reply names the guild and the one
thing that unblocks them. The officer surface is a **durable** message
(`postAuditMessage`, not the 15-second auto-deleting reply), because it is the
only place an officer can see that someone is waiting.

**4. Cross-guild presence is information, not a verdict.**
The `gm_find_player_by_uid` call and the `uid_registered_elsewhere` error are
gone. The target guild's own roster answers the only question being asked. Which
other guilds hold that UID is read separately and goes into the officer message
and the audit metadata.

**5. Refusals are audited under their own action type.**
`discord_verification_refused`, with `p_service = 'discord-profile-verification'`
and `p_level = 'WARN'`. `logPlayerAction` gained optional `service` / `level` for
this: without them every row a caller writes is filed as the Player Portal, which
is how every `discord_verification` row in production ended up attributed to
`member-portal`.

**6. The worker grants the extra member role only to a confirmed member.**
`addVerifiedRole` is now reachable only under `result.role === "guild_member"`.

## Consequences & Invariants

- **A guild role is never granted without a roster row in that tag's own guild,
  on the verification channel's own game server.** Not by OCR, not by the
  worker's second role grant, not as a fallback.
- **Nothing in this path names a tenant or a game server.** The scope comes from
  `guilds.server_number`, the gate from `guild_config`, the tag from
  `guild_config.guild_tag` falling back to the guild's own id. The
  `DEFAULT_GUILD_TAGS` table is deleted — it was the ADR-003 violation that
  finding H2 already removed from the frontend, re-created in
  `supabase/functions/`, and two of its seven values were wrong.
  `tests/discord_verification.test.js` now walks `supabase/functions/` to keep it
  from coming back a third time.
- **A truncated or failed roster read is an error, never "absent".** Refusing a
  real member on a partial read is the one failure mode that would look exactly
  like the feature working.
- **The gate is opt-in, so protection is data.** A guild created tomorrow is
  unprotected until its admin ticks the box. This is a deliberate owner decision
  (2026-09-27): PSA and STW build their rosters through this flow today, and
  defaulting the gate on would have stopped their onboarding without asking them.
- **Business logic stays in `_shared/discord-verification.ts`.** The Edge
  Function remains the thin caller for OCR, the by-name Discord role lookup and
  every Discord-facing action. Both halves are pinned by
  `tests/discord_verification.test.js`.
